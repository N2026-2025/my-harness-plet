# PLE Agent Harness — Plan, Build, Verify

A small autonomous agent harness for the
[Physical-Engineering's Last Exam (PLE)](https://kaggle.com/competitions/physical-engineerings-last-exam)
competition.

**In one sentence:** it connects to the competition evaluator, uses an LLM to
plan and complete an engineering task inside the task's Linux container, writes
every requested deliverable to its exact path, verifies its own work, and
returns a final summary.

## How a task is solved

`serve.py` runs one loop per task (`solve(session)`), split into three roles:

1. **Planner** — inspects the task files with read-only tools and produces a
   plan: every deliverable with its exact path and format, the method to use,
   how to verify it, and structured citations (clause + value + source).
2. **Worker** — creates skeletons for **all** deliverables immediately, then
   fills them in small verified steps. It computes with code rather than by
   hand, tracks citations, and watches the remaining time.
3. **Verifier** — opens every deliverable, checks it against the task, and
   recomputes key numbers. It replies `PASS` or a numbered list of gaps.
4. **Fix rounds** — up to 2 rounds: the worker fixes the reported gaps and
   re-verifies.
5. **Wrap-up** — before the deadline, tools are disabled and the model writes
   its final summary. Files already written still count.

```
Evaluator ──WebSocket──▶ taskbridge.Session ──▶ task container (bash + files)
                                                    │
                                              task MCP servers
serve.py
   Planner ──plan──▶ Worker ──summary──▶ Verifier
                       ▲                     │
                       └───── fix gaps ──────┘
```

## Running it

The evaluator runs the harness through `submission.yaml`:

```yaml
install: create a Python 3.12 venv and pip install -r requirements.txt
serve:   python serve.py
```

`serve.py` calls `taskbridge.run(solve)` and listens on `$PORT` (default
`8765`). The evaluator supplies the task, the container, and the model
credentials over the WebSocket connection.

For a quick local syntax check (no evaluator needed):

```powershell
python -m py_compile serve.py taskbridge.py
```

### Environment variables

| Variable | Purpose |
|---|---|
| `MODEL_NAME` | Model ID to call (from `model_api`) |
| `MODEL_BASE_URL`, `MODEL_API_KEY` | OpenAI-compatible endpoint credentials |
| `REASONING_EFFORT` | `low` / `medium` / `high` (defaults to `max` for Claude/GLM, `high` otherwise) |
| `MAX_OUTPUT_TOKENS` | Output cap per model call (default 32,000) |
| `COMPACT_AT_TOKENS` | Prompt size that triggers context compaction (default 150,000) |
| `PORT` | Port the WebSocket server listens on |

## What makes it robust

- **Deliverable-first strategy** — an early empty deliverable beats a late
  missing one; skeletons are created before detailed work starts.
- **Plan → verify loop** — hard constraints are checked explicitly instead of
  assumed, with up to two fix rounds.
- **Streaming responses** — supports Chat Completions and the Responses API,
  with reasoning content and Claude thinking blocks preserved.
- **Retries with backoff** — `408`, `409`, `429` and `5xx` wait 5/15/30/60/120 s.
  `400` errors are treated as bugs and fixed by adjusting the request (context
  recovery, `max_tokens` fallback, dropping `reasoning_effort`, shrinking output,
  or switching API), not blindly retried.
- **Context compaction** — old tool results are truncated first; if still too
  large, earlier turns are replaced by model-written notes; unread results are
  truncated only as a last resort.
- **MCP support** — task tools are exposed directly when the catalog is small,
  otherwise through `mcp_find` / `mcp_call`. Connections are cached across fix
  rounds.
- **Time budgeting** — each model call has a deadline with a finish margin
  (180 s, shrunk on short tasks). Verification only starts if enough time
  remains for the round plus wrap-up.
- **Prompt caching** — Claude models mark up to 4 messages with
  `cache_control: ephemeral` to cut input cost.

## Customizing

- **Model** — change `model_api` in `submission.yaml`. Supported families:
  - Gemini: `google-cloud/gemini-4-argon`, `google-cloud/gemini-3.8-flash`,
    `google-cloud/gemini-3.1-pro-preview`
  - Claude: `google-cloud/claude-opus-5-5`
  - Gemma: `google-cloud/gemma-4-26b`
  - Open-weight: `google-cloud/gpt-oss-120b`, `google-cloud/glm-5.2`,
    `google-cloud/llama-4-maverick`
- **Verification rounds** — `MAX_FIX_ROUNDS` in `serve.py` (default 2).
- **Context window** — lower `MAX_OUTPUT_TOKENS` in `submission.yaml` for models
  with smaller windows (Gemini: ≤65,536).
- **Artifacts** — always generate them with the same `model_api` you submit.
  The official judge re-scores independently, so local judge scores do not
  affect ranking.

## Known issues / notes

- `artifacts/` is a placeholder and **must be regenerated** before submission.
- The harness currently targets `google-cloud/gemini-3.8-flash`; test other
  models on the dev set before changing `submission.yaml`.
- `install.ps1`, `guia-ple-kaggle.md`, `.kilo/`, `WRITEUP.md`, and
  `REMAINING_STEPS.md` are local development files and can be excluded from the
  final Kaggle commit.
- Two verification rounds match the paper's finding that hard constraints need
  explicit verification.
